# ZSpace Memo：Todo 任务管理功能扩展需求

> 原文记录（产品负责人，2026-11-23）。设计响应见 [`../DESIGN.md`](../DESIGN.md)。

## 一、产品定位调整

目前规划的 Todo 功能过于简单，只有任务名称、完成状态和简单列表，不足以满足日常任务管理需求。

希望将它设计成一个完整的 Todo / 任务管理工具，参考系统日历和成熟 Todo 软件的交互方式。

核心原则：

1. 快速添加任务：可以只输入标题，立即创建。
2. 完整任务管理：点击任务后，可以设置日期、时间、提醒、重复规则、优先级、分类和详细内容。
3. 周期性任务：支持日常、每周、每月、每年等重复任务。
4. 多端统一：Windows、macOS、Web、Homepage 使用同一套任务数据和后端 API。
5. 数据仍然存储在极空间原生独立记事本中，一条普通任务对应一条极空间笔记。

不要将本项目设计成只有勾选框的简单 Todo List。

## 二、任务数据设计

每条任务对应极空间记事本中的一条笔记，统一放在专门创建的分类中，例如：

```text
极空间记事本
└── ZSpace Memo
    ├── 任务 A
    ├── 任务 B
    ├── 任务 C
    └── ...
```

任务至少包含以下业务属性：

| 属性 | 说明 |
|---|---|
| 标题 | 必填，任务名称 |
| 详细内容 | 任务描述、备注、补充信息，支持多行文本 |
| 完成状态 | 未完成、已完成 |
| 开始日期 | 可选 |
| 开始时间 | 可选 |
| 截止日期 | 可选 |
| 截止时间 | 可选 |
| 全天任务 | 支持全天，不必指定具体时间 |
| 时间段 | 可以设置开始时间和结束时间 |
| 提醒规则 | 不提醒、准时提醒、提前提醒、自定义提醒 |
| 重复规则 | 每天、每周、每月、每年、工作日、节假日、农历、自定义 |
| 优先级 | 低、普通、高、紧急 |
| 分类 | 任务所属业务分类 |
| 标签 | 支持多个标签 |
| 创建时间 | 任务创建时间 |
| 更新时间 | 最后修改时间 |

注意：开始时间、截止时间和提醒时间是不同概念，不能混为一个字段。

例如：

任务：续费 eSIM

- 开始日期：2026-11-24
- 截止日期：2026-11-26
- 截止时间：18:00
- 提醒：提前一天、提前一小时
- 重复：每半年
- 优先级：普通
- 备注：记录充值金额、运营商和续费链接。

## 三、日期和时间选择器

日期和时间选择是 Todo 的重要功能，建议参考系统日历、手机日程软件的交互方式。

日期选择器至少支持：

1. 日期选择。
2. 时间选择。
3. 全天任务。
4. 开始日期和结束日期。
5. 开始时间和结束时间。
6. 快捷日期：今天、明天、后天、下周、自定义。
7. 时间段选择。
8. 清除日期和时间。

界面可以参考我提供的日期选择器截图。

日期选择器要支持公历显示，并为后续农历日期和农历重复预留扩展能力。

## 四、提醒功能

提醒与任务截止时间独立设置。

支持以下提醒方式：

- 不提醒。
- 到期时提醒。
- 提前 5 分钟。
- 提前 10 分钟。
- 提前 15 分钟。
- 提前 30 分钟。
- 提前 1 小时。
- 提前 1 天。
- 自定义提前时间。

允许同一任务设置多个提醒。

例如：11月26日18:00截止，可以设置11月25日18:00和11月26日17:00分别提醒。

提醒通知需要考虑：

1. Windows 桌面系统通知。
2. macOS 桌面系统通知。
3. Web 浏览器通知。
4. PWA 通知。
5. 后续扩展邮件、其他消息推送渠道。

重要：不能仅依赖桌面客户端运行来触发提醒。

因为用户可能关闭 Windows 或 macOS 客户端。提醒调度应该由部署在极空间 NAS 上的后端服务负责。

需要设计统一的提醒调度机制，确保任务到期时能够触发通知。客户端负责接收和展示通知。

通知功能需要考虑权限申请、重复发送防护、失败重试、时区及夏令时。

## 五、重复任务

重复规则需要作为核心功能设计，而不是简单地给任务加一个重复标记。

第一版需要考虑：

| 重复类型 | 示例 |
|---|---|
| 每天 | 每天检查工作邮件 |
| 每周 | 每周一整理工作 |
| 每月 | 每月24日续费 |
| 每年 | 每年生日提醒 |
| 每半年 | 每半年续费 eSIM |
| 工作日 | 周一至周五提醒 |
| 节假日 | 指定节假日重复 |
| 农历 | 农历生日、节日 |
| 自定义 | 每隔 N 天、N 周、N 个月等 |

每周需要允许选择星期几。

每月需要考虑：
- 每月指定日期，例如每月 24 日。
- 每月最后一天。
- 每月第一个星期一等规则。

每年需要支持指定月日。

自定义规则需要允许指定间隔，例如：
- 每隔 3 天。
- 每隔 2 周。
- 每隔 6 个月。

对于不存在的日期，需要明确处理策略，例如每月31日遇到没有31日的月份时，跳过还是按月末执行。

### 重复任务的完成逻辑

重复任务不能因为完成一次就将整个任务标记为永久完成。

需要支持：

- 完成本次。
- 跳过本次。
- 修改本次。
- 修改整个重复系列。
- 终止整个重复系列。

例如：每月24日续费 eSIM。

11月24日完成后，下一次自动生成12月24日的待办，不需要用户手动创建。

建议使用一个系列任务 ID 和每次执行的 occurrence（发生实例）来管理重复任务。

但需要保持前面的核心存储原则：一个重复任务系列对应一条极空间原生笔记，不能为了每次重复就无限创建笔记。

已完成的发生实例需要有记录，避免重复完成、重复提醒或修改后丢失历史状态。

## 六、任务详情界面

点击 Todo 列表中的任务，打开完整任务详情。

任务详情至少包括：

### 基本信息
- 任务标题。
- 详细描述。
- 完成状态。
- 优先级。
- 分类和标签。

### 时间安排
- 开始日期。
- 开始时间。
- 截止日期。
- 截止时间。
- 全天任务。
- 时间段。

### 提醒设置
- 是否提醒。
- 提醒时间。
- 多个提醒。
- 提醒渠道。

### 重复设置
- 是否重复。
- 重复类型。
- 重复间隔。
- 重复结束日期。
- 重复发生次数。
- 重复实例管理。

### 其他信息
- 创建时间。
- 修改时间。
- 完成时间。

详细内容采用文本编辑器，第一版不要求复杂富文本，但应支持多行文本、链接、基本 Markdown。

打开详情后，应当可以随时编辑任务，不应只允许修改标题和完成状态。

## 七、任务列表与视图

不要只有一个简单列表。

至少规划以下视图：

1. 收集箱：没有明确安排日期的任务。
2. 今天：今天需要处理的任务。
3. 即将到来：未来有截止日期的任务。
4. 已逾期：已经超过截止时间且未完成的任务。
5. 全部任务：查看全部任务。
6. 已完成：查看历史完成任务。
7. 重复任务：查看周期性任务。

列表中显示：
- 完成状态。
- 任务标题。
- 截止日期或时间。
- 优先级。
- 重复标识。
- 提醒标识。

支持按日期、优先级、创建时间排序。

支持搜索任务标题和详细内容。

可以根据屏幕大小切换紧凑列表和常规列表。

## 八、快速添加与完整编辑

桌面悬浮窗口仍然保留，但定位为快捷入口。

快速添加：
- 输入标题。
- 回车创建。
- 默认进入收集箱。
- 可以快速设置日期。
- 可以快速设置优先级。

点击任务后进入详细编辑界面，可以完善日期、提醒、重复、备注等信息。

不要将所有复杂配置都堆在悬浮窗口里。

建议采用两个层次：

第一层：轻量快捷 Todo 悬浮窗口。

第二层：完整任务管理界面。

Windows 和 macOS 保持一致的核心交互。

Web 页面和 Homepage 嵌入模式也可以访问任务列表、详情和编辑功能。

## 九、底层存储和架构要求

继续遵守项目之前确定的技术架构：

- FastAPI：统一业务后端。
- React + TypeScript：统一前端。
- Tauri 2：Windows 和 macOS 桌面端。
- Web/PWA：浏览器和手机访问。
- Homepage：通过 iframe 或适配组件嵌入。
- zspace_skill：复用极空间原生记事本能力。

极空间原生笔记仍然是任务数据的唯一事实来源。

### 元数据存储

由于极空间原生记事本目前已确认的主要数据字段为笔记 ID、标题、HTML 正文、分类、标签等，而截止时间、优先级、提醒和重复规则尚未确认存在对应原生字段，因此需要设计任务元数据映射方案。

建议将任务详情和结构化元数据保存在笔记正文中，采用可解析的结构化格式。

但必须先验证：
1. 自制工具写入元数据后，极空间原生记事本是否能够正常编辑。
2. 原生记事本修改正文后，是否会破坏自定义元数据。
3. 自制工具重新读取后，元数据能否完整恢复。

不能假设 HTML 自定义属性、隐藏标签或注释一定能被官方编辑器完整保留。

若无法可靠保留，先研究兼容性更好的存储格式，再确定正式实现方式。

允许使用辅助数据库保存提醒调度状态、通知订阅、发送记录和缓存，但不能把任务的真实内容、状态和配置另外复制成一套独立 Todo 数据源。

### 后端接口扩展

除了原生笔记 CRUD，还应设计任务业务 API，例如：

- GET /api/v1/tasks
- POST /api/v1/tasks
- GET /api/v1/tasks/{id}
- PUT /api/v1/tasks/{id}
- DELETE /api/v1/tasks/{id}
- POST /api/v1/tasks/{id}/complete
- POST /api/v1/tasks/{id}/skip
- GET /api/v1/tasks/today
- GET /api/v1/tasks/upcoming
- GET /api/v1/tasks/overdue
- GET /api/v1/tasks/repeating

提醒和重复任务也应有相应的管理接口。

接口设计要考虑未来不仅有 Todo，还可能继续扩展普通笔记、文件管理等极空间能力。

## 十、开发优先级

不建议第一版把所有复杂能力同时实现，但架构必须支持完整功能。

### P0：核心任务能力
- 新增、编辑、删除、完成任务。
- 任务详细内容。
- 截止日期、截止时间。
- 全天任务和时间段。
- 优先级。
- 分类和标签。
- 今天、即将到来、逾期、已完成视图。

### P1：日程与提醒
- 提前提醒。
- 多提醒。
- NAS 后端提醒调度。
- Windows、macOS 和 Web 通知。
- 每天、每周、每月、每年重复。
- 每半年等自定义重复。

### P2：高级重复能力
- 工作日。
- 节假日。
- 农历重复。
- 自定义复杂重复规则。
- 跳过本次、修改整个系列。
- 重复任务历史管理。

### P3：后续扩展
- 子任务。
- 附件。
- 更丰富的 Markdown 编辑。
- 邮件或其他通知渠道。
- 日历视图。
- Homepage 深度集成。

## 十一、开发要求

请先根据以上需求完善产品设计和数据模型，再进入编码。

重点注意：

1. 不要将 Todo 简化为只有标题和勾选框。
2. 日期、截止时间、提醒时间、重复规则必须独立建模。
3. 重复任务要有发生实例及完成历史管理。
4. 提醒必须考虑 NAS 后端独立运行，不能依赖桌面端一直开启。
5. 所有平台共享统一业务 API。
6. 保持极空间原生笔记的双向兼容。
7. 不要重复实现 zspace_skill 已经具备的记事本基础功能。
8. 复杂功能分阶段实现，但数据结构和接口不能因为第一版简单而限制后续扩展。

请先产出更新后的功能结构、任务数据模型、重复规则模型、提醒调度方案和页面交互设计，再开始开发。
